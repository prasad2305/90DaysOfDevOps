# Linux File System Hierarchy (the most important directories)

# Let's understand where things live in Linux

# Linux File System Hierarchy

### / (root)
The starting point of the Linux file system. All files and directories are located under it.

**I would use this to:** Navigate to the top level of the file system.

---

### /home
Contains home directories of normal users where they store their personal files.

**I would use this to:** Access user files and directories.

---

### /root
Home directory of the root (administrator) user.

**I would use this to:** Store files and configurations that only the root user should access.

---

### /etc
Stores configuration files for the operating system, services, and applications.

**I would use this to:** View or update application and system configurations.

**Examples:**
- `/etc/environment` → Stores system-wide environment variables.
- `/etc/adduser.conf` → Stores default settings for new users.

---

### /var/log
Stores log files generated by the operating system, services, and applications.

**I would use this to:** Troubleshoot issues and monitor system activity.

**Examples:**
- `auth.log` → Contains login and authentication logs.
- `syslog` → Contains general system and service logs.

---

### /tmp
Stores temporary files created by users and applications.

**I would use this to:** Store temporary data that is not needed permanently.

---

# Additional Directories (Good to Know):

### /bin
Contains essential Linux commands required for basic system operations.

**I would use this to:** Access commonly used commands like `ls`, `cp`, `mv`, and `cat`.

---

### /usr/bin
Contains additional user commands and application binaries.

**I would use this to:** Run applications such as `git`, `curl`, and `python3`.

---

### /opt
Used to install optional or third-party applications.

**I would use this to:** Store software that is not part of the default operating system.

# Scenario 1: Service Not Starting

A web application service called `myapp` failed to start after a server reboot.

### Step 1 : `systemctl status myapp`

**Why:** Check whether the service is running, failed, or inactive.

### Step 2 : `journalctl -u myapp -n 50`

**Why:** View the last 50 log entries to identify startup errors.

### Step 3 : `systemctl is-enabled myapp`

**Why:** Verify whether the service is configured to start automatically during boot.

### Step 4 : `systemctl list-dependencies myapp`

**Why:** Check if any required dependency service failed to start.

### Step 5 : `systemctl restart myapp`

**Why:** Restart the service after identifying and fixing the issue.

### Step 6 : `systemctl status myapp`

**Why:** Verify that the service started successfully after restart.

---

## Troubleshooting Flow

- Check whether the service is running or failed
- Review service logs for errors
- Verify service is enabled at boot
- Check service dependencies
- Restart the service if needed
- Confirm service is running successfully

# Scenario 2: High CPU Usage

Your manager reports that the application server is slow.

### Step 1 : `top`

**Why:** View live CPU and memory usage.

### Step 2 : `ps aux --sort=-%cpu | head -10`

**Why:** Display the top 10 processes consuming the most CPU.

### Step 3 : `pgrep -a <process-name>`

**Why:** Find the PID of a specific process.

### Step 4 : `ps -p <PID> -o pid,ppid,%cpu,%mem,cmd`

**Why:** View detailed information about the high-CPU process.

### Step 5 : `kill <PID>`

**Why:** Gracefully stop the process if it is stuck or consuming excessive CPU.

### Step 6 : `kill -9 <PID>`

**Why:** Forcefully terminate the process if it does not stop with the normal kill command.

### Step 7 : `top`

**Why:** Verify that CPU usage has decreased after the process was terminated.

# Scenario 3: Finding Service Logs

A developer asks for the logs of the Docker service.

### Step 1 : `systemctl status docker`

**Why:** Verify the current status of the Docker service.

### Step 2 : `journalctl -u docker -n 50`

**Why:** View the last 50 log entries.

### Step 3 : `journalctl -u docker -f`

**Why:** Follow logs in real time as new entries are generated.

### Step 4 : `journalctl -u docker --since "1 hour ago"`

**Why:** View Docker logs generated within the last hour.

### Step 5 : `journalctl -u docker | grep -i error`

**Why:** Search for error messages in Docker logs.

# Scenario 4: File Permission Issue

A script located at `/home/user/backup.sh` is not executing due to permission issues.

### Step 1: `ls -l /home/user/backup.sh`

**Why:** Verify the current file permissions.

### Step 2: `chmod +x /home/user/backup.sh`

**Why:** Make the script executable.

### Step 3: `ls -l /home/user/backup.sh`

**Why:** Confirm that execute permission was added successfully.

### Step 4: `./backup.sh`

**Why:** Verify that the script executes successfully after fixing permissions.
